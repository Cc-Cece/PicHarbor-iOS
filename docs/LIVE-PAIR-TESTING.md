# 0.2.4 原始 Live Photo 配对测试说明

## 0.2.5 复测补充

用户在 0.2.4 实测：Motion Photo 双条目按格式特性接受；原始配对联合提交表现最好；先照片后视频可完成但偶发静态显示或多次重试。两种原始方式对旧照片通常一次完成，对新拍照片偶发资源数 0 的准备阶段 SOURCE_CHANGED。

0.2.5 修复本地版本冻结后的重试问题，详见[新拍照片修复与验收](FRESH-PHOTO-FIXES.md)。优先直接继续旧失败任务，再分别备份刚拍摄的 Live Photo。若仍仅显示静态图，请区分“任务等待云端确认”和“任务已完成后仍不播放”，记录实际路径与错误码。该反馈不能代替所有格式、官方保存取回及配额矩阵验收。

本版本保留 Motion Photo（默认），新增两种可执行实验方式。服务器处理、配额及官方客户端识别行为均须真机验证。

| 设置 | 实际处理 |
| --- | --- |
| 原始配对 · 联合提交（测试） | 两个资源分别传输后通过 livePhotoInfo 关联；已有原图时自动使用 reconcileInfo 补视频 |
| 原始配对 · 先照片后视频（测试） | 先提交或查到原图，再传视频，通过 reconcileInfo 关联到原图 |
| Motion Photo | 原有封装方案，保持默认和历史任务设置 |

两种原始配对方式不改写源资源，不把 MOV 单独提交为普通视频，不导入派生资产到本机图库。原始与编辑版本分别配对；三个画质模式沿用原设备/策略映射，设置名称不能替代实际配额验收。

## 测试顺序

1. 同一 Sideloadly Apple 账号及应用标识覆盖安装。先关闭 PicHarbor 自动备份，测试期间也关闭 Google Photos 自动备份，避免它先行上传样本而只测到去重。使用少量专用 Live Photo，保留本机原件。
2. 首先选“仅原始版本”与“联合提交”，备份一张从未上传的新 HEIC Live Photo。应显示两项资源及实际联合路径，随后两个哈希指向同一云端项目，再完成动态确认。
3. 使用另一张新 Live Photo 测试“先照片后视频”。也可用云端确实仅有原始静态图的专用样本验证补动态；无需为测试删除既有媒体。
4. 相同原始内容已配对时再次备份会查询去重。比较两条真实上传路径应使用各自未备份的新样本。
5. 检查 Google Photos：是否一个动态项目、本机原件是否标记已备份、声音/关键帧/方向/时间是否正常、详情及账号配额情况。
6. 保留本机原件，观察官方客户端是否识别已在设备上；如执行保存，记录是否新增资产及动态表现。动态播放通过不能代替身份验收。
7. 基础样本通过后，再用原始与编辑后均保留测试裁剪、旋转、关键帧及 HDR。不同版本确有不同内容时可能形成两个云端项目，须与错误重复区分。
8. 测试断网、暂停、终止和重开。结果不明的配对只查询，不无条件重复提交。

## 原有任务与异常

- 旧 applePair 设置值对应联合方式。资源数为 0 的 PAIR_PROTOCOL_UNVERIFIED 任务可继续/重试，新版会执行原始导出与关联。切换另一种路径需创建新任务或按当前设置重新备份，旧任务仍固定内容策略。
- 旧 Motion Photo 与原始图片是不同内容，本版不会合并或删除旧云端封装项。建议先用新样本检查同机显示。
- 配对确认要求照片普通哈希查询、视频 PhodeoMovie 查询返回同一远端 ID，之后检查动态标记与处理状态；两个文件各自存在不算完成。
- PAIR_CONFIRMATION_PENDING：保留提交状态，仅继续查询；可立即重新确认，长期不变化时反馈脱敏诊断及实际路径。
- PAIR_COMMIT_REJECTED：服务器明确拒绝关联，进入需处理状态，不退化为独立视频或 Motion Photo。
- 本地上传响应的确定性错误发生在提交前时才允许重新传输；含糊网络错误保持提交围栏。
- Live Photo 清理仍关闭。诊断新增 pair_routes 与 pair_pending_submissions，仅含计数，不含令牌、哈希、远端 ID 或照片内容。
