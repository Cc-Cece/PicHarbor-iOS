# Live Photo 云端确认：研究依据与后续建议

整理日期：2026-10-19（Asia/Shanghai）。本文汇总讨论和源码研究，不代表候选接口已通过 PicHarbor 真机验证，也不承诺谷歌的处理时限。

## 1. 已知现象与判断边界

- 用户在 0.2.5（构建 7）反馈：官方谷歌相册可见对应 Live Photo，任务的两个资源均显示“云端已确认”，整体仍等待“确认云端内容”。诊断包含 `REMOTE_MOTION_NOT_DYNAMIC`。
- 用户随后观察到至少一张照片最终变成绿色“已备份”，任务创建至完成约 15 分钟。这说明至少该样本能够通过当前检查；不能据此认定动态字段始终无法解析。
- 创建到完成包含排队、资源准备、上传、提交和确认。尚无该样本的分阶段耗时，不能将全部 15 分钟归因于确认或谷歌处理。
- 诊断是所有任务的汇总，错误码列表没有与具体任务绑定，不能按数量直接对应当前照片。
- 原始配对中，两个资源被标记确认，表示照片哈希和按动态视频类型查询的视频哈希指向同一云端项目。它是关联证据；最终的处理完成、动态可用检查仍是另一层。

0.2.5 的最终检查要求项目已进入图库状态、回收站状态正常、处理状态为 `100`，且 gpmc 解析得到动态标记。重复读取完整图库、最长五分钟的确认退避、协议调用串行排队，都可能增加应用侧等待。各自贡献仍需测量。

## 2. 官方与开源项目的做法

### 2.1 Google 官方公开 API：保存 ID，定向读取处理状态

官方建议保存稳定媒体 ID，使用 `mediaItems.get` 查询单项，或 `mediaItems.batchGet` 一次查询最多 50 项。视频处理状态区分 `PROCESSING`、`READY`、`FAILED`。可借鉴的是“按当前项目读取状态”的模式。[S1][S2]

适用限制：公开 Library API 当前只能读取该应用创建的内容，并要求相应 OAuth 权限。不能假定 gpmc 的凭据、内部媒体标识或上传结果可直接用于该 API。[S2][S3]

公开文档没有给出官方 iOS 客户端完整的内部确认算法。PhotosBackup 对官方客户端的逆向记录是第三方、特定版本的研究，不能当作 Google 的正式接口保证。[S4]

### 2.2 PhotosBackup：照片哈希与动态视频类型查询

该项目通过内容哈希查询存在性；配对视频查询额外指定 `PhodeoMovie` 类型，区别于普通独立视频。其提交方法取得云端标识后返回上传成功，未在该方法中等待完整图库动态标记。因此，它的成功状态与 PicHarbor 的最终动态就绪标准不能直接等同。[S5]

可借鉴：按资源角色查询、上传前查重、保留提交结果。不能仅凭另一个项目更早显示成功，就认定它以同样强度证明了动态播放或恢复完整性。

### 2.3 Cloudified：共同云端标识与提交证据

该项目的配对查询要求照片及动态视频哈希指向同一个最终云端标识；两者分别存在并不足以证明关联。它保留提交返回的证据，配对导致初始标识变化时，可回查共同的当前标识，避免无依据地重新上传已接受的组件。[S6]

可借鉴：同一项目约束、持久化提交保护、结果不明时先查询。共同标识本身仍不等于视频已经处理完或原始资源已完整验证。

### 2.4 gotohp：联合提交返回成功标识

检查的 Live Photo 主流程上传两个组件、执行联合提交，取得非空媒体标识后返回成功，没有在这段流程中增加完整图库动态标记等待。[S7]

可借鉴：将文件传输与配对提交明确分开。其返回条件不能直接作为 PicHarbor 的完整动态验收或本地清理资格。

## 3. 推荐的确认方式

| 层次 | 要证明的事实 | 推荐证据与处理 |
| --- | --- | --- |
| 提交接受 | 服务端接受了本次提交 | 保存返回结果、账号及提交保护状态；超时不直接重提 |
| 资源存在 | 对应内容可查询 | 使用本任务固化的内容哈希，区分普通照片、普通视频及动态视频 |
| 原始配对 | 照片与动态视频属于同一项目 | 两个哈希查询得到相同的当前云端标识；不同或缺失时继续核对 |
| 动态就绪 | 动态资源处理完成、可访问 | 优先验证单项目接口能否提供可靠字段或资源访问证据；不足时使用图库状态补充 |
| 本地清理 | 当前账号及完整资源满足清理标准 | 独立核验内容、云端状态和原件访问；删除前重新检查并由用户确认 |

单项目候选入口是现有 gpmc 的 `get_download_urls`、`get_stream_manifest`，分别位于 `Vendor/gpmc/api.py`。它们已有按媒体标识发起请求的实现，但尚需验证：能否取得苹果原始配对的视频成员、能否识别处理未完成、返回的究竟是原件还是转码资源。不能预先把这些入口认定为完整替代方案。

官方说明，视频下载参数 `dv` 可返回高质量转码视频，Motion Photo 也可用该参数获取动态部分。因此，可访问或可播放的转码视频不能用来证明原始 MOV 字节一致。[S1]

动态字段缺失应保留“证据不足”与具体原因，不能直接推断上传丢失，也不能为了提速而跳过最终检查。Motion Photo 与苹果原始配对可以使用不同适配器，但每种证据的含义必须明确。

## 4. 实施顺序

### 第一步：测量并减少应用侧等待

1. 每条任务分别记录准备、传输、提交接受、配对确认、动态确认开始、最终完成的时间；旧任务未记录的时间保持未知。
2. 每轮记录查询类型、耗时、结果原因、检查次数、下次检查时间；区分协议队列等待与实际网络请求耗时。耗时测量优先使用单调时钟。
3. 待确认任务释放上传并发名额，使用独立、有界的确认调度；共用串行 Python 引擎时也应避免长查询持续阻塞提交。
4. 多任务共享账号内的图库状态，保留增量同步令牌；完整分页成功后原子发布，失败不把部分结果当成有效证据，令牌失效时才退回完整同步。
5. 提交后先进行有限次数的短间隔检查，之后退避。间隔由真机测量及服务端限流反馈调整，不以无限高频查询换取表面提速。
6. “立即检查”跳过应用安排的等待时间；不保证绕过服务端处理或限流，也不触发重新上传。

### 第二步：验证定向动态检查

1. 以已经通过官方客户端播放的样本，研究单项目返回字段和动态资源访问方式。
2. 与现有图库检查并行比对，记录两者首次给出有效证据的时间及不一致原因。
3. 覆盖普通视频、静态图、错误关联和未处理完的反例；证明不会将它们误判为完整 Live Photo。
4. 候选检查通过协议回归和真机矩阵后，再决定是否用于最终通过条件；保留明确的补充核验路径。

### 第三步：状态展示和升级

- 分别显示“已提交”“配对已确认”“等待动态就绪”“完整确认完成”，说明当前还缺什么证据。
- 资源行避免仅用“云端已确认”概括所有层次。配对成功状态不能直接授予本地删除资格。
- 已上传的旧任务保留资源、云端映射及提交保护，升级后继续查询，无需为了新的确认逻辑重传。
- 原始联合提交继续作为优先对比对象；先照片后视频保留补充关联用途，Motion Photo 保留为格式选择。本文不修改默认策略。

## 5. 整理时的代码进度

整理时仓库为 0.2.6，提交 `84601fb7485bf898b92cf45194100b96d4a25e51`。与讨论中的 0.2.5 相比，代码已包含部分优化：

- `BackupModels.swift`：配对状态、确认次数和时间字段，独立确认重试计数，5／10／20／30 秒的退避目标间隔。
- `HarborModel.swift`：Live 确认释放上传名额，上传与确认分开限流，保存最近一次确认耗时及完成时间。
- `HarborRootView.swift`：配对与确认进度、最近查询耗时、下一次检查及立即重新确认入口。
- `harbor_protocol.py`：15 秒状态缓存，保留增量同步令牌；分页使用所属输入上下文，失败清除证据，完成后发布快照。

上述是本机源码核对，不等于本轮重新完成构建或真机验收。该版本最终动态判断仍依赖图库快照中的处理状态及 `is_micro_video`，定向动态接口尚未作为通过条件。后续应在现有实现上补测量、实测和适配，避免重复实现已有调度逻辑。

本机依据：[任务模型](../Sources/Core/BackupModels.swift)、[任务流程](../Sources/Core/HarborModel.swift)、[界面](../Sources/Features/HarborRootView.swift)、[协议与同步](../Python/harbor_protocol.py)、[gpmc 接口](../Vendor/gpmc/api.py)。

## 6. 验收与安全边界

- 样本：新拍／旧照片，联合提交／先照片后视频／Motion Photo，原始／编辑后版本，HEIC／JPEG、HDR、方向、声音和关键帧。
- 场景：小／大云端图库、批量任务、断网、暂停重启、提交响应丢失、动态处理中、错误配对、云端不可访问、增量令牌失效及同步中途失败。
- 测量：分别报告排队、上传、配对及动态确认耗时；样本足够时统计中位数、P95、请求数和重复上传数。创建至完成总时间不替代分阶段时间。
- 结果：不因定向接口返回模糊结果而错误完成；未知提交先查后重试；确认等待期间后续上传仍可推进；官方客户端动态播放和保存回 iPhone 均单独记录。
- 诊断只包含任务关联用的随机标识、状态、原因、时间、时长和计数；不导出凭据、签名地址、内容哈希、云端标识、照片内容或完整文件名。
- 原件访问核验与本地删除继续独立设计。不得因“提交成功”“共同标识”或“能播放转码视频”而自动降低清理标准。Live Photo 清理能力的开放仍需独立验收。
- 成功目标是减少应用造成的等待并准确展示剩余条件，不承诺 Google 在固定秒数内完成处理。
